# Main web dashboard

19 October 2026 · Local UI prototype

The main UI runs at [localhost:8000](http://127.0.0.1:8000). Follow the [README setup](../README.md#run-the-main-dashboard). React, TypeScript, Vite, React Router and shared CSS build the frontend; FastAPI serves the app and its API. MLflow provides real experiment and registry evidence inside the same UI.

The sidebar uses the original [Sime Darby Property logo](https://www.simedarbyproperty.com/home/images/sdp-logo-coloured.png?v2) and the browser tab uses its [official favicon](https://www.simedarbyproperty.com/home/favicon.png?v3), downloaded from the [official website](https://www.simedarbyproperty.com/home/). Both are served locally from `web/public/brand/` with their colours and aspect ratios preserved. SimeGuardian remains the product name.

## Views

The top bar and sidebar follow the same five-page demo journey: **Overview → Monitoring → Model training → Anomaly detection → Rescue**, linking to `/overview`, `/pipeline`, `/training`, `/demo` and `/response`. Opening `/` takes operators to the standalone township Overview at `/overview` and responders to Rescue. The same navigation stays available in the fullscreen map. Its shared row is 64px high (80px on phones), with a 1050px maximum tab area and matching typography on every stage; page controls sit below it. Phase links use native view transitions: the active highlight and number morph between tabs over 360ms while content briefly fades and enters. Reduced-motion preferences disable the animation; browsers without the API navigate normally. The sidebar contains the same five pages and starts hidden; use the menu button to show or hide it. Its visibility is retained during navigation and resets on page reload. Responders see the five top-bar pages but can navigate only to Rescue, which is their only sidebar item; switching roles still uses the existing explicit control.

Model training includes the recorded model evolution chart, validation metrics and run comparisons. **View training data** opens the dataset explorer; **Advanced model controls** reveals links to detailed evaluation and the registry, where promotion and rollback remain explicit. Anomaly detection keeps the registered-model replay controls and **Inspect current trace** link to inference or the current incident. Overview contains the township map dashboard, while Monitoring contains the usage heatmap and six-signal detail. Both pages link to each other and retain household, utility, period, pause and demo state during navigation between them. Operations remains accessible directly at `/operations`.

## Demonstrate the journey

1. Open **Anomaly detection**, choose **Quiet household**, and click **Load scenario**.
2. Click **Run registered model**. The backend loads the registered numeric champion, scores the four-feature window and applies the replay policy. A model anomaly with corroborating utilities creates one incident and a simulated family notification.
3. Open the trace. Advance **+5 minutes** for the resident stage, then another **+5 minutes** for township assignment. Deadlines come from persisted family notification creation time. Page refresh does not restart them.
4. Click **Switch to responder**. This requests a separate local bearer session. The server denies operator evidence to this session and returns only assigned check-ins.
5. **Accept responsibility**, then **Record completed check-in** with an outcome. Acceptance keeps the incident open; the completed outcome resolves it.
6. Return to the operator to inspect the shared result. Resetting this replay preserves all dataset and MLflow evidence and appends a local reset audit record.

Other scenarios demonstrate missing water, resident activity, away status and usual activity. Missing water is represented as missing, skips model scoring and blocks incident creation. Resident activity and away status block new inactivity incidents even if the model scores the window as anomalous.

## Evidence and boundaries

The model fixture is deterministic: seed 42, 496 initial training windows, 736 updated training windows (including initial), and 360 fixed validation windows. Training and validation households and days differ. Labels are excluded from model inputs. The final test set has not been generated or used. Training is real batch retraining; recorded versions alone do not prove better field performance.

The source explorer independently generates 23,520 records for 120 synthetic households across six source groups. It is UI development evidence, not a causal input pipeline for the trained model. Parking/gate records from the same synthetic trip retain a shared evidence group and shared attribution.

The pipeline simulation covers all 120 source-fixture household IDs, with deterministic early, daytime, evening and split routines. Each home has its own timing, consumption level, daily variation and weekend timing; these are illustrative profiles, not inferred resident attributes. Township totals are available for 24 hours (hourly bins), 7 days (six-hour bins) and 30 days (daily bins), summing each home's simulated hourly amounts. Each signal is aggregated separately in its native unit. The average per home covers that same period.

The Putra Heights 3D explorer lives on the Overview page and opens fullscreen by default in a landscape top view (north points right), framed around the monitored neighbourhoods. The entire geographic model remains available through pan and zoom. Its operations layout is inspired by [Navexa WMS](https://dribbble.com/shots/26041365-Navexa-WMS-Warehouse-Management-Dashboard), using the Sime Darby red, neutral surfaces, rounded cards and Metropolis typography specified in [DESIGN.md](DESIGN.md). The top bar selects the utility and history period; the KPI strip shows monitored households, detected demo anomalies, and township electricity/water totals. The left floating panel lists searchable households (ID, neighbourhood or routine), with All / Anomalies filters. Search and filters affect only this list, not township totals, map markers or the underlying dashboard heatmap. Selecting a row locates its footprint. The right floating panel inspects the selected household and can run the existing anomaly demonstration.

Both panels can be collapsed. View controls, “Show all patterns” and the usage legend sit above the map. Two floating bottom cards show electricity and water history using the same simulation window, with native units, MYT bucket tooltips and independent collapse controls. Empty household data shows missing totals rather than invented readings. On screens up to 1,000px wide, side panels start closed; opening one closes the other and temporarily hides the bottom cards to preserve space. Selecting a household from the list closes the mobile panel to reveal its location. “Overview” or Escape exits the fullscreen map; “Fullscreen” expands it without rebuilding the scene. “Inspect all six signals” opens Monitoring at the selected household’s signal detail. The native dialog manages modal focus, and background scrolling is restored on exit. Top view uses drag/pinch/scroll to pan and zoom while preserving the landscape orientation, including household focus and camera reset. The 3D view retains orbit controls.

The geographic snapshot contains 15,857 OpenStreetMap building footprints, 3,667 road/rail/water segments, mapped land-use areas and the complete mapped township boundary, with Mapzen/SRTM elevation for the hill and surrounding terrain. One scene unit represents ten metres. Terrace rows follow actual footprint geometry; façades, pitched roofs and individual trees are procedural estimates. Most building heights are inferred, with source height or floor metadata available for 313 footprints. Roads and rail follow terrain height; bridge elevations and detailed building interiors are not modeled. Source coverage and freshness are not guaranteed.

The explorer shares household selection, period, utility layer, pause and detected-anomaly state with the charts. Each of the 120 mapped `SG-*` homes starts as a compact usage-coloured marker; selected or flagged homes display a usage-history sparkline, heat strip and period total when space permits. “Show all patterns” enables these cards for the other homes. Leader lines connect displaced cards to dots on the actual mapped footprints. Dense cards fan out to avoid each other, the header, floating panels, controls and charts; smaller screens collapse some cards to dots, with full details available through zoom and the inspector. The selected household and detected anomaly take priority. Each marker is anchored just above the modeled roof at a point inside its mapped footprint; the roof perimeter is outlined. Hover or selection exposes latitude/longitude (WGS84) in the map card, with six-decimal coordinates and an OpenStreetMap footprint link in the inspector. Coordinates identify a derived footprint point, not a surveyed GPS measurement. A staggered 2.8-second pulse indicates simulated monitoring; the dot stays visible throughout. Pausing the simulation or enabling reduced motion removes the pulse.

Roof and dot colours show the latest time bin relative to that home's own average in the selected window, using the same blue → cyan → green → amber → red bands as the household heatmap (below 0.5×, 0.5–1×, 1–1.5×, 1.5–2×, and at least 2×). Each sparkline scales to its own peak and the heat strip runs oldest to newest. These usage colours do not establish an anomaly. A confirmed demo concern overrides the affected roof with red and adds a red outlined card, an explicit “!” marker, an anomaly count and a “Locate anomaly” action. Flags appear only after the existing corroborated detection rule passes, and disappear when the demo is cleared. The map controls use the existing simulation and do not create replay incidents or notifications.

Inspector totals remain in electricity kWh and water litres over the selected period. The 120 demo homes occupy distinct mapped footprints, with 20 in each of six neighbourhood groups. The original 24 assignments are retained; 96 additional residential roofs were selected from the same geographic snapshot on 21 October 2026. These positions are reproducible through the map preparation script, but their IDs and readings are synthetic and have no relationship to actual residents or meters. The remaining mapped buildings have no readings. Building geometry is batched, trees are instanced, rendering runs on demand, and resources are released on navigation. Failed map downloads or unavailable WebGL retain accessible readings and the 2D reference, with a retry control.

Google Maps satellite view was inspected to improve urban density, road alignment and roof appearance; no Google imagery is bundled. The aerial-photo view has been removed. The township map remains available in the map controls; links to The Glades masterplan and Serasi Type A apartment floor plan remain in the attribution footer. The previously downloaded aerial is retained only as source material. The apartment floor plan is not applied to the simulated landed houses. The UI links to Google satellite for comparison and displays OSM and terrain attribution. See [map sources and reproducible extraction instructions](../web/public/township/SOURCES.md) for the downloaded assets, ODbL database licence, elevation sources and estimation limits. All reference downloads and map extraction took place on 20 October 2026.

The household heatmap compares each bin with that home's average bin value within the selected window. A blue → cyan → green → amber → red scale shows increasing usage, with labelled bands below 0.5×, 0.5–1×, 1–1.5×, 1.5–2× and at least 2× the home's average. Colour represents usage, not risk or a learned normal range. Searching filters heatmap rows only; township totals continue to include all homes. Selecting a row or using the household selector updates the six-source 24-hour detail. Each detail curve is scaled to its own peak for that household/window; cards and tooltips retain native hourly values. Parking/gate share trip activity and must not be counted as independent evidence.

One second advances 15 simulated minutes. Pause freezes both views, reduced-motion preferences start them paused, and a refresh restarts the illustration. It does not advance replay time, change datasets, run inference or create incidents. The four current model inputs remain explicitly tied to SG-001's separate replay, regardless of the household selected in the illustration.

**Run anomaly demo** starts a nine-second walkthrough for the selected household: normal routine, a utility drop, a cross-check of supporting signals, and an illustrative detected concern. It selects the 24-hour electricity view, reduces both utilities to 4% of their generated normal values in a recent window, and suppresses movement/app events there. The expected-versus-observed chart, six-source detail and township totals share those altered readings. The demonstration rule requires both utilities below 20% of their usual values and no conflicting activity; the affected home is marked in coral, while its affected time cells retain their usage colours with a dark outline and diagonal stripes. This is not registered-model inference, a health-risk score, or a real incident/notification.

Pause/continue freezes the walkthrough and simulation together. Replay restarts it; Clear demo, changing households or leaving the Overview/Monitoring pair removes the local demonstration. Reduced-motion preferences disable the scan, pulse and curve transitions while retaining the explicitly started step-by-step walkthrough. The registered-model demo link opens the existing replay controls for a separately recorded inference.

Replay state and reset audit records persist in `artifacts/dashboard/workspace.db`. Local jobs use `dashboard.db`; MLflow owns its separate tracking store and artifacts. Keep all of these when preserving a demonstration. Reset changes only the current replay. Completed incident history across replay resets is not a production incident archive.

Notification creation and escalation are **simulated**. No phone notification delivery, receipt, worker heartbeat or latency is invented. Explicit clock advancement drives replay deadlines; a production scheduler, device transport and retries are pending. Incident creation records its model version; registry changes affect later explicit scoring.

Production accounts/consent, PostgreSQL incident constraints, full six-source feature construction, episode-level rule/model/combined evaluation, validation threshold experiments, iOS delivery, sustained AI recovery, handoffs/cancellation, help requests and withdrawal are not complete. Local role switching is intentionally available to anyone with loopback access. Keep the service bound to loopback. The full [implementation plan](IMPLEMENTATION_PLAN.md) remains the integration checklist.

## Verification

`uv run --locked pytest -q` in `backend/` covers reproducibility, real MLflow runs and model actions, training jobs, replay deadline boundaries/restart/stale updates, responsibility, reset preservation, deterministic source records, role scope and missing utilities.

`npm run build` and `npm run test:e2e` in `web/` check TypeScript/build, actual Chrome browser workflows, stable routes, dataset filters, UI training/registry actions, incident/responder flow, failure recovery and mobile width. Browser tests operate on the local synthetic stores and append real tracking/audit evidence.
